# 组织体系重构与智课复用 · 方案设计（v6 · 已决策 / 待实施）

> 目标：把「班级」从教师私有物上收为学校组织实体，教师只维护「课程内容 + 授课关系」；学生获得稳定的行政班与学籍状态；课程内容通过「复用」在学期之间滚动，AI 资产（讲稿 / 配音 / 向量）零重生成。

## 0. 已确认决策（2026-10-29）

| # | 决策 | 落地影响 |
|---|---|---|
| 1 | **学生单班**：一个学生同时只属于一个行政班 | 事实源是 `ClassStudent` 的占用关系（**不加 `User.classroom` 冗余字段**），由 DB 条件唯一约束兜底；转班 = 旧关系置 `transferred` + 新关系 active（**不是 removed**，见 X-05 / X-09） |
| 2 | **教师不保留建班** | 班级写操作仅管理员；教师端 `ClassManage` 降级为只读名单 + 学习数据；移动端教师建班页同步下线 |
| 3 | **复用不带题库**（列为可选） | 复制清单默认勾选排除 `Question`；弹窗必须显式提示"题库/作业/考试不会复制" |
| 4 | **毕业可登录、可看全部历史内容** | 不做"只能看已完成章节"的裁剪。课程随学期结束自然停止维护，刷课不产生任何意义（成绩/统计窗口已关闭） |
| 5 | **引入学期字典** | 新增 `Term` 表，`Course.term` 由 CharField 改为 FK（设计见 §12） |
| 6 | **转专业不留旧课** | 学生端只显示当前班课程；旧班课程入口消失，历史成绩仍可在"我的考试/错题本"查到。不做选课/补修关系 |
| 7 | **班级不设负责人** | `ClassRoom.teacher` **保留字段**，降级为"建班人"记录，不参与任何权限判断；"负责人"只在课程维度存在，即 `Course.teacher`（创建者）。详见 §4.1.1 |
| 8 | **不做课程团队 / 课程共享** | 本期只有"课程创建者"一种教师身份。通过 §4.2.1 的函数抽象预留扩展点，后续按实际使用量再评估（结论见 §13） |
| 9 | **导入支持自动建班** | 学生导入时班级编码不存在可自动建班，但必须在预览页列出待建清单并勾选确认；班级另有独立导入入口。三类导入共用「预览页 → 结果页」（见 §3） |
| 10 | **不引入专业 / 学院维度** | 系统只管到班级。专业、学院信息由班级名称承载（如"计算机2401"），系统不解析、不建字段、不做筛选（见 §4.1.2） |

> 本文档 v6 完成导入流程扩展与范围收敛，共 **33 条**冲突（§11），其中 X-01 / X-02 / X-03 为**阻断项**。v6 变化：§3 重写为「三类批量导入 + 自动建班 + 预览/结果页」；移除专业维度（`ClassRoom.major` 不新增）；X-32（班级编码未归一）、X-33（自动建班留空班）为 v5 新增。

## 1. 现状盘点：四个结构性问题

| # | 现状（代码位置） | 问题 |
|---|---|---|
| 1 | 注册已关闭：`PlatformSetting.register_open` 缺省 False（`users/views.py:36-46`）；学生导入仅「用户名 + 姓名」两列（`platform_admin/user_import.py`），且没有班级导入入口 | 教师账号无导入通道，只能管理员逐个建；学生导入不落班级，导完还要教师手动拉人；一届几十个班只能逐个点 |
| 2 | `ClassRoom.teacher` 必填，班级由教师创建（`classroom/views.py:32`）；教师只能看到自己建的班（`common/access.py:38`） | 同一个行政班会被 3 位任课教师各建一次，学生被拉进 3 个"班"，统计口径直接分裂 |
| 3 | `POST /api/classes/join/` 凭 8 位邀请码即可入班（`classroom/views.py:146`）；无审核、无人数上限、无个体回收 | 邀请码是"写入权限凭证"，一旦外泄任何人可加入；发现错乱只能关闭整班或重新生成，个体成员无法撤销，`ClassStudent` 留不下"谁在何时用什么码进来的" |
| 4 | 班级创建强制至少一门课程（`classroom/serializers.py:41`），且只能挂自己的课 | 管理员先建班、后配课的正常顺序被这条约束挡住 |
| 5 | `Course.term` 是自由文本，无学期字典、无唯一约束；每学期新建课程要重新上传 PPT、重新跑讲稿和配音 | 一学期一次的 AI 生成成本（TTS 按页计费）被重复支付；教师没有"沿用上学期内容"的路径 |
| 6 | `User` 无班级、无学籍字段；`ClassStudent.learn_status` 只管"在不在这个班" | 学生毕业后无法表达"已毕业"；历史数据无限累积，班级名单、统计分母永远包含已毕业学生 |
| 7 | 作业、考试直接挂 `(course, classroom)` 双外键（`homework/models.py:34`、`exams/models.py:18`） | 班级是教学运行的容器，不能只做成"课程的标签"；这也决定了复用课程时运行数据不能跟着复制 |
| 8 | 学生可见课程不过滤 `Course.status`（`common/access.py:22-26`），只按在册班级反查 | 复用产生的新课程一旦挂班，本学期学生立刻看到下学期内容；这是复用功能上线前必须补的洞 |

**根因**：系统把「组织」（谁和谁是一个班、学生读到第几年）和「教学」（谁给这个班上什么课）揉在了同一张表里，教师既是内容生产者又是组织维护者。注册关闭后，组织数据必须由学校侧（管理员）供给，这个职责必须切出来。

## 2. 目标模型：三层职责分离

```
组织层（管理员）           教学层（教师）              资产层（随课程复制）
─────────────────         ─────────────────          ─────────────────
ClassRoom 行政班           Course 课程（一学期）       Catalog 章节树
  ├ code 班级编码            ├ term 学期                 ├ PPTResource + 页图
  ├ 届别/学制                ├ teacher                  ├ TeachingVideo(讲稿+配音)
  └ status                   └ reused_from 溯源          ├ CourseResource
User 学生                    ClassCourse 授课关系         ├ Material + Chunk(向量)
  ├ classroom ─┐              ├ classroom                └ Question 题库
  ├ edu_status ├─ 决定可见性   └ course
  └ 入学年/学制 ┘            Homework / Exam (course × classroom)
```

三条铁律：

1. **一个学生同时只属于一个行政班**（占用关系唯一，由条件唯一索引保证），转专业/复读走"转班"，留痕不并存。
2. **一门课程只属于一个学期**（沿用现有 `Course.term`），跨学期靠"复用"产生新课程，不共享可变内容。
3. **班级跨学年存在**（4 年制班存在 4 年），课程按学期挂进来，`ClassCourse` 只增不减（撤销除外）。

## 3. 功能 A：三类批量导入（班级 / 教师 / 学生）

### 3.1 统一导入管道

现有 `user_import.py` 的「解析 → 逐行校验 → 预览 → 事务创建」已经跑通，不新写一套，抽成三类共用的导入器：

```
ImportSpec(kind, columns, validator, writer)
  build_template(spec)         生成模板 xlsx（含填写说明页）
  parse_excel(file, spec)      按 spec 读列，缺列报错
  annotate_rows(rows, spec)    逐行校验，附 status/message
  commit(rows, spec, options)  事务写入，返回结果汇总
```

三类导入共用同一套「预览页 → 结果页」组件，只有列定义、校验器和写入器不同：

| kind | 模板列 | 写入 |
|---|---|---|
| `class` | 班级编码、班级名称、入学年、学制、状态（可选） | 建 `ClassRoom` |
| `teacher` | 工号、姓名 | 建 `User(role=teacher)` |
| `student` | 学号、姓名、**班级编码**（可空）、班级名称（可选）、入学年（可选） | 建 `User(role=student)` + `ClassStudent` + 可选建班 |

- 初始密码规则不变：`Zk + 用户名后 6 位`，首次登录 `must_change_password=True`
- 单次上限：学生/教师 500 行、5MB；班级 200 行（一个学校一届通常几十个班）


### 3.2 接口

```
GET  /api/admin-panel/imports/template/?kind=class|teacher|student
POST /api/admin-panel/imports/preview/     multipart: file, kind
POST /api/admin-panel/imports/commit/      json: kind, rows[], options
```

`options`：

```json
{
  "default_enrollment_year": 2026,
  "default_duration_years": 4,
  "skip_invalid": false,
  "create_missing_classes": true
}
```

- `default_enrollment_year / default_duration_years`：自动建班时的兜底参数，模板里没填就用它
- `skip_invalid`：是否剔除错误行继续导入，**默认关闭**（见 3.7）
- `create_missing_classes`：是否允许自动建班，默认开启但必须在预览页确认清单

旧路径 `/admin-panel/users/import/*` 保留一个版本做兼容（移动端与旧前端），内部转调新 service。

审计：`AdminActionLog` 增加 `Action.CLASS_IMPORT`、`Action.USER_IMPORT` 的 `target_label` 带角色与数量（"批量导入 32 个学生 / 新建 4 个班级"）。

### 3.3 班级导入（独立入口）

先把班级建好、学生后到，是最稳的流程，也是大校区的常规做法。

| 列 | 必填 | 校验 |
|---|---|---|
| 班级编码 | ✅ | 3–32 位，字母数字与 `-`；系统内唯一、表内唯一（大小写与首尾空格归一后比较） |
| 班级名称 | ✅ | ≤200 字；同编码不存在时用于建班 |
| 入学年 | ✅ | 2000–2100，且 `入学年 + 学制` 不超过 2100 |
| 学制 | ✅ | 3 / 4 / 5（允许 2，专升本场景） |
| 状态 | ⬜ | 空 = `active`；可填 `preparing` / `active` |

**已存在的编码不覆盖**，标为 `skipped` 并提示"编码已存在，未修改"。理由：覆盖会改掉已有班级的学制/届别，进而影响在读学生的毕业年份计算，属于高危操作。要改请走单条编辑。

### 3.4 学生导入与自动建班

这是本次新增的关键能力：**不先建班也能直接导学生，编码不存在时自动建班**。

自动建班规则（按顺序判定）：

| # | 情况 | 处理 |
|---|---|---|
| 1 | 编码在系统已存在且状态为 `active` / `preparing` | 直接入班，不新建 |
| 2 | 编码在系统已存在但状态为 `graduated` / `archived` | 该行 `error`："班级已毕业/归档，不能再分配学生" |
| 3 | 编码不存在，且 `create_missing_classes=true` | 列为**待建班级**，预览页列出清单待确认 |
| 4 | 编码不存在，且开关关闭 | 该行 `error`："班级编码不存在" |
| 5 | 文件内多次出现同一编码 | 只建一次（取首次出现的名称/届别），其余行复用 |

建班字段来源（优先级从高到低）：

```
班级名称  ← 模板「班级名称」列 → 编码兜底（预览页标黄提示"将以编码作为名称"）
入学年    ← 模板「入学年」列 → 向导 default_enrollment_year
学制      ← 向导 default_duration_years（模板不设该列，一次导入通常同一学制）
```

**为什么不做"静默自动建班"**：编码打错一个字（`CS-2401` vs `CS-24001`）就会造出一个空壳班，学生已经分进去，事后清理要逐人调班。所以自动建班必须满足两个条件——预览页**列出将新建的班级清单**、管理员**勾选确认**后才执行。

两条硬约束（都容易漏）：

1. **编码必须先归一**：`strip().upper()` 后再比较与落库。SQLite 的 `UNIQUE` 区分大小写，`CS-2401` 与 `cs-2401` 会共存成两个班，学生被劈成两半。`username` 唯一性已经这么处理了（`user_import.py:111` 用 `Lower()`），班级编码要跟上，且写在模型 `save()` 里，不依赖调用方。
2. **空班不创建**：某编码下的学生行如果全部校验失败，不能只留一个班。建班条件加一条——**该编码至少有 1 行合法学生**；预览页的待建清单标注"预计 N 人"，N=0 的不进入提交。

### 3.5 逐行校验规则（学生）

| 校验 | 提示 |
|---|---|
| 用户名非空、≥6 位、无空格、≤150 | 用户名至少 6 位（用于生成初始密码） |
| 用户名系统内唯一（不区分大小写） | 该用户名已被使用 |
| 表内不重复 | 与表内其他行用户名重复 |
| 姓名非空、≤64 | 姓名不能为空 |
| 班级编码存在，或可自动创建 | 班级编码不存在（未开启自动建班时） |
| 目标班级状态可入班 | 该班级已毕业/已归档，不能再分配学生 |
| 学生当前无其他班 | 该学生已在「XX班」，请先调班（单班制不允许重复入班） |
| 班级人数上限 | 超出班级容量（若启用容量字段） |

> 人数上限是可选功能。若不设上限，预览页要显示"该班导入后将达 N 人"，让管理员对人数有个数。

### 3.6 预览页与结果页（三类共用一套）

**预览页**（导入前，前端一个组件 `ImportPreview`）：

| 区块 | 内容 |
|---|---|
| 统计条 | 总行数 / 可导入 / 有错误 / 将新建班级 N 个 |
| 待建班级清单 | 编码、名称（可编辑）、届别、学制、**预计人数**；N=0 的不提交；未勾选则该班学生行转为错误 |
| 错误行表格 | 行号、原始值、错误原因；分页 |
| 选项 | 「忽略错误行，仅导入合法行」（默认关闭）；「自动创建不存在的班级」（默认开启） |
| 操作 | 确认导入 / 返回重传 |

**结果页**（导入后）：

| 区块 | 内容 |
|---|---|
| 结果汇总 | 成功 N 人、跳过 M 人、失败 K 人、新建班级 J 个 |
| 新建班级列表 | 编码 + 名称，点击进入班级名单 |
| 失败明细 | 行号、原因、原值；**支持下载失败行 xlsx**（带原因列，改完可直接重传） |
| 快捷入口 | 查看学生名单 / 下载初始密码表 / 再导一批 |

初始密码表是学校最实际的诉求：导出"学号、姓名、班级、初始密码"，便于线下分发。这个也沿用现有规则生成，不额外存储密码。

### 3.7 事务边界与幂等

**单事务**包住三类写入：班级创建 → 用户创建 → `ClassStudent` 关联 → 审计。任一行失败整体回滚，不会出现"班建了、学生没进去"的半成品。

`skip_invalid=true` 时，错误行在 **commit 之前**就被剔除（用服务端重新校验的结果，不信任前端），事务内只剩合法行——不是"边导边失败"。

**幂等**：重复上传同一文件

- 学生：用户名唯一性拦住，全部报"该用户名已被使用"，不会重复建账号
- 班级：编码唯一性拦住，标 `skipped`，不会重复建班
- 因此无需额外的"导入批次去重"机制


### 3.8 与现有数据的关系

现有学生账号 8 个、教师 2 个（开发库），生产仅 `admin` + `wgy`。导入功能不需要迁移历史数据，只需保证新导入的学生落到一条 `ClassStudent`（见 5.2 占用唯一规则）。

## 4. 功能 B：班级归口管理端

### 4.1 模型变更 `ClassRoom`

| 字段 | 变更 | 说明 |
|---|---|---|
| `code` | 新增 `CharField(32, unique)` | 班级编码，导入匹配键；管理员建班必填 |
| `teacher` | **降级保留**：`null=True, blank=True`，`on_delete` 改 `SET_NULL` | 语义改为"建班人"，仅作记录，不参与任何权限判断（详见 4.1.1） |
| `enrollment_year` | 新增 `PositiveSmallIntegerField` | 届别，如 2024（2024 级） |
| `duration_years` | 新增 `PositiveSmallIntegerField(default=4)` | 学制 3/4/5 |
| `status` | 取值扩展 `preparing / active / graduated / archived` | 现有 `open/closed` 需数据迁移映射（open→active, closed→archived） |
| `invite_code` / `invite_enabled` | 保留字段，默认 `invite_enabled=False` | 见 4.4 |
| `graduate_year` | 计算属性 | `enrollment_year + duration_years` |

`ClassRoom` 与 `Course` 的关联保持 `ClassCourse` 中间表不变（无需改结构；可选加 `term` 冗余便于筛选，非必需）。

**新建班级默认 `active`**：管理员建班通常就是"这个班现在开始用"，默认 `active` 才能立刻出现在教师的"可选班级"列表里。`preparing` 只用于"提前建班、暂不公开"的少数场景（例如招生名单未定），建班时显式勾选。若默认 `preparing`，教师挂课时会看到空列表，误以为系统坏了。

### 4.1.1 `ClassRoom.teacher` 为什么保留、为什么不再使用

系统里「负责人」这个词被三种完全不同的东西共用过，必须先拆清：

| 概念 | 定义 | 系统里落在哪 |
|---|---|---|
| **行政班班主任** | 学校给行政班配的辅导员，管学生、学籍、考勤 | **系统里不存在，也不需要**。学籍动作全部由管理员执行 |
| **课程负责人** | 创建课程、对内容和质量负责的教师 | `Course.teacher`（已有，就是创建者） |
| **课程团队成员** | 被负责人拉进来一起备课/批改的教师 | 目前**不存在**，本期不做（§13） |

`ClassRoom.teacher` 不属于任何一种。它的真实语义是"谁点了建班按钮"——以前教师自己建班，这个字段顺带被当成了教学权限的判定依据（19 处，见 4.2.1）。

**保留字段的三个理由**：

1. 库里已有值（6 个班），删列需要"改引用 → 置空 → 观察一版 → RemoveField"三步，收益为零
2. 它记录了"这个班当初是谁建的"，是一条有用的审计线索（虽然 `AdminActionLog` 也有，但班级列表页看得到更直观）
3. 保留一个不再被读取的字段，比删掉它更安全——万一有遗漏的引用，是"读到旧值"而不是"AttributeError 500"

**但必须做两件事，否则保留就是隐患**：

| 动作 | 原因 |
|---|---|
| `on_delete` 改 `SET_NULL` + `null=True` | 现在是 `CASCADE`：**删一个教师会连带删掉他建的班**，进而级联删作业、考试、成绩（见 X-25） |
| 19 处权限判断全部移到课程维度 | 只要还有一处读 `classroom.teacher`，就会有人以为它是"班主任"并继续加逻辑 |

**明确禁止**（写进模型 docstring，防止后来人误用）：

- serializer 不可写该字段；前端建班表单不再出现"负责人"
- 任何新代码不得用 `classroom.teacher` 做权限判断、可见性过滤、统计口径
- 管理端班级列表如需展示，列名写"建班人"，不写"班主任/负责人"

**字段语义**：

```python

    settings.AUTH_USER_MODEL, null=True, blank=True, on_delete=models.SET_NULL,
    related_name="created_classes", verbose_name="建班人",
    help_text="仅记录建班操作人，不参与任何权限判断（权限一律走 Course.teacher）",
```

教师能看到哪些班，答案唯一且清晰：**我教的课挂过的班**。

### 4.1.2 暂不引入专业 / 学院维度

**明确不做的**：`ClassRoom.major`、学院表、专业表、专业负责人、培养方案，一律不加。

理由不是"以后再说"，而是加了就要连带：

| 加一个专业字段 | 会连锁要求 |
|---|---|
| 班级要选专业 | 专业字典维护（谁来建、改名怎么办） |
| 有专业就要有学院 | 学院表、学院管理员、跨学院统计 |
| 按专业筛选/统计 | 编码规则、报表维度、权限边界全要跟着改 |
| 专业对应培养方案 | 课程与专业的归属关系、学分要求 —— 这是教务系统的核心，不是本系统的范围 |

系统只需要回答一个问题：**这个学生属于哪个班**。专业信息由班级名称承载（"计算机2401"、"软件工程2302"），人能看懂，系统不解析。

**反模式提醒**：不要先加一个 `major = CharField(blank=True)` "备用"。字段一出现，导入模板就会加列、前端就会加筛选、报表就会加维度，最后长成一棵残缺的组织树——每一层都只有个名字，没有任何实际约束和校验。等真要按专业统计时再建完整三级结构，比现在塞半成品便宜得多。

**将来值得做的触发信号**（任一出现再立项）：

- 需要按专业汇总学情或毕设数据
- 需要跨班选课 / 学分认定
- 需要"专业负责人"这一角色审批课程

|---|---|---|
| 课程教师 | `course.teacher == me`，且班级已挂该课 | 发布/批改作业、发考试、看学习统计、看答卷、AI 生成、挂班 |

**权限函数分两层，为将来的课程团队留口子**（见 §13）：

```python
# apps/common/access.py
def teacher_can_manage_course(user, course) -> bool:
    """课程管理权。现在等价于"课程创建者"；将来接课程团队时只改这个函数体。"""
    if is_platform_admin(user):
        return True
    return bool(user.is_teacher and course and course.teacher_id == user.id)

def teacher_teaches(user, course, classroom=None) -> bool:
    """教学权 = 能管这门课 + 班级已挂该课。"""
    if not teacher_can_manage_course(user, course):
        return False
    return classroom is None or ClassCourse.objects.filter(course=course, classroom=classroom).exists()
```

全站现在有 **41 处** `course.teacher == user` 的裸判断。这次改造时不要只把 `classroom.teacher` 换掉，而是**统一换成 `teacher_can_manage_course()`**——现在多花半天，将来加课程团队时只改一个函数体，41 处调用一行不用动。这是本次改造最划算的一笔投资。

### 4.3 教师选班交互

课程详情页（或课程列表行操作）新增「授课班级」：抽屉列出"可选班级"（管理员建的 active/preparing 班，按届别筛选 + 搜索），勾选提交。

- `GET  /api/classes/available/?course=<id>&keyword=&year=`  → 未被本课关联的 `active` / `preparing` 班
- `GET  /api/courses/<id>/classes/`  → 已关联
- `POST /api/courses/<id>/classes/`  `{classroom_ids: []}` → 批量挂接
- `DELETE /api/courses/<id>/classes/<classroom_id>/`

允许挂 `preparing` 班（开学前备课的正常场景）：挂接不等于曝光，学生能不能看到由**班级状态**决定——`preparing` 班的学生看不到任何课程，班级置 `active` 后自动出现。这比"教师挂课时才校验状态"更灵活，也少一个阻断点。

挂接即生效：该班在册学生立刻能在"我的课程"看到这门课。**但这会带出第 8 条现状问题**——所以必须同时做：学生可见课程过滤 `status=active` 且所属 `ClassRoom.status=active`；教师准备就绪后再把课程置 active（课程表单已有状态字段，前端把它做成显式"发布"动作）。

**另一个越权点，两种情况都要堵**：`analytics/views.py::_resolve_classroom_course` 在**不传** `course` 时取 `classroom.courses.order_by("id").first()`；在**传了** `course` 时只校验"该课程属于这个班"，**没有校验这门课是不是我的**。

改造前班级只属于一个教师，两条路径都安全；改造后一个班有多位教师：

- 不传 course → 教师 A 默认落到教师 B 的课
- 传 `?course=<B的课>` → 直接越权，人都不用猜

三处视图（班级统计 / 班级导出 / 学生详情）共用这个函数，改一处即可：

```python
def _resolve_classroom_course(request, class_id):
    qs = ClassRoom.objects.all() if is_platform_admin(request.user) else classrooms_for_user(request.user)
    classroom = qs.filter(id=class_id).first()
    if not classroom:
        return None, None, api_response(message="班级不存在或无权查看", code=404, status=404)

    course_id = request.query_params.get("course")
    # 教师只能解析到自己的课（管理员不限）
    course_qs = classroom.courses.all() if is_platform_admin(request.user) \
                else classroom.courses.filter(teacher=request.user)

    if course_id:
        course = course_qs.filter(id=course_id).first()
        if not course:
            return None, None, api_response(message="该课程未关联到此班级，或你无权查看", code=403, status=403)
    else:
        course = course_qs.order_by("id").first()
        if not course:
            return None, None, api_response(message="你在该班级暂无授课课程", code=403, status=403)
    return classroom, course, None
```

## 5. 功能 C：学生学籍与状态流转

### 5.1 字段设计

**先纠正一个前提（v7 修订）**：现有 `User` **没有** `classroom` 字段（已核对 `apps/users/models.py`，全库仅 `role / real_name / phone / avatar / must_change_password`）。学生与班级的唯一关联就是 `ClassStudent`。因此本节**不新增 `User.classroom`**，理由见 5.2。

`User` 新增（仅 `role=student` 有意义）：

| 字段 | 类型 | 说明 |
|---|---|---|
| `edu_status` | CharField choices | `enrolled` 在读 / `suspended` 休学 / `graduated` 已毕业 / `withdrawn` 退学转出 |
| `enrollment_year` | PositiveSmallIntegerField(null) | 入学年份，默认继承班级 |
| `duration_years` | PositiveSmallIntegerField(null) | 学制，默认继承班级（3/4/5） |
| `status_changed_at` | DateTime(null) | 状态变更时间 |
| `status_note` | CharField(200, blank) | 变更原因（转专业/休学一年等） |

**"当前在哪个班"不落字段**：由 `ClassStudent` 中 `learn_status ∈ {active, inactive}` 的那一条决定（占用关系唯一，见 5.2）。这样"学生属于哪个班"只有一个答案来源，不存在两处数据打架。

学制与届别**挂在班级**，学生字段是可覆盖的冗余（应对个别提前/延期毕业）。理由：一个行政班天然同届同学制，让管理员填 300 次不如填 1 次。

**"年级"不落库**：`当前年级 = 当前学年 - enrollment_year + 1`，由后端算。落库会每年需要一次全量刷新，且留级/跳级后必然错。

**毕业 / 退学都不是终态**：休学可复学（已建模），退学后重新入学、毕业批次撤销（授位审核退回）也都是真实场景。`edu_status` 允许回退，但每次变更写 `status_changed_at + status_note` 与审计日志，不做"一次写死"。

### 5.2 单班约束与写入口（关键，v7 重写）

**单一事实源 = `ClassStudent`**，不引入 `User.classroom`。分工：

| 表/字段 | 语义 | 谁写 |
|---|---|---|
| `ClassStudent`（`active`/`inactive`） | 学生当前所在班（占用关系，**全库唯一**） | 只允许 `apps/classroom/services.py` 写 |
| `ClassStudent`（`transferred`/`removed`） | 历史关系（转班/退学留痕，不占位） | 同上，只增不改不删 |
| `User.edu_status` 等学籍字段 | 学籍状态（在读/休学/毕业/退学） | 毕业批处理、学籍变更 service |

**为什么不再加 `User.classroom`**：那样会变成"同一事实两处存储"，必须双写 + 防漂移 + 巡检兜底；而 108 处业务代码全部读 `ClassStudent`，加字段反而制造第二个真相。改用一个**条件唯一索引**把"单班"变成数据库强制事实，比任何巡检都硬：

```python
class ClassStudent(BaseModel):
    class Meta:
        constraints = [
            models.UniqueConstraint(
                fields=["student"],
                condition=models.Q(learn_status__in=["active", "inactive"]),
                name="uniq_occupied_class_per_student",
            )
        ]
```

- `active` 与 `inactive` 都算"占位"，否则学生在 A 班 inactive、在 B 班 active 就绕过单班（`INACTIVE` 目前是全库死枚举，无任何写入方，为兼容存量仍纳入条件）
- `transferred` / `removed` 不占位，允许同一学生留多条历史
- 违反约束时抛 `IntegrityError`，必须被 service 转成人类可读的 409，**不能让它冒到接口层变成 500**

> **存量数据卡口**：当前开发库已有 1 条违反单班的记录——学生 `20249999`（姓名"多班学生"）同时是 `网络2026届-1班` 与 `数据结构B班` 的 active 成员。加约束前必须人工指定归哪个班（另一条置 `transferred`）。**迁移脚本检测到冲突时中止并打印清单，绝不自动挑一个**。

写入口收敛到一个 service，禁止散落 `ClassStudent.objects.create`：

```python
# apps/classroom/services.py
def assign_students(classroom, students, *, operator, note=""):
    """入班唯一入口。学生已有占用关系时抛 AlreadyAssigned（附当前班级），
    由调用方决定是 transfer 还是中止——禁止静默覆盖。"""

def transfer_students(classroom, students, *, operator, note=""):
    """调班：旧关系置 transferred（不是 removed！），新班建 active，同一事务。
    transferred 保留历史可见性——置 removed 会让学生看不到旧班的成绩与答卷。"""

def remove_students(classroom, students, *, operator, reason=""):
    """退学/转出：learn_status=removed，edu_status=withdrawn。"""
```

配套两条硬规则：

1. **禁止物理删除 `ClassStudent`**：`ClassStudentViewSet` 现在允许 `DELETE`，硬删会丢留痕、也让"退学"和"从没来过"分不清。改为 delete 落到 `remove_students`（软删）。
2. **禁止 serializer 直接写 `learn_status`**：`ClassStudentSerializer` 的 `learn_status` 改只读，一切状态流转走 service。

再加巡检命令 `manage.py audit_class_consistency`，判定规则写死：

```python
# 对每个 role=student 且 is_active=True 的用户：
# 一致 = 恰有 0 条或 1 条占用关系（active/inactive）
# 未分班 = 0 条 → 一致（新生名单先到是常态）
# 不一致：多条占用（约束加不上时的历史脏数据）/ 班级状态与 edu_status 矛盾
#         （如 ClassRoom.status=graduated 但学生仍 enrolled）
# transferred、removed 关系不参与判定（它们是历史）
```

### 5.3 状态机

```
enrolled ──休学──────→ suspended ──复学──→ enrolled
   │
   ├──毕业批处理──→ graduated ──撤销/重新入学──→ enrolled
   │
   └──退学/转出──→ withdrawn ──重新入学──→ enrolled
```

（状态可回退，每次变更记录 `status_changed_at + status_note` 与审计；不做"一次写死"。）

- 毕业**不自动**执行：学校毕业审批时间不统一，且需人工确认名单。提供"届别毕业"批处理 + 列表预警（`今年应毕业：2020级+4年`）。
- 班级状态随之流转：`preparing`（建班未开课）→ `active`（在读）→ `graduated`（整班毕业）→ `archived`（归档）。
- **状态与班级状态不强制联动**：个别学生提前毕业时，班级仍为 active，只改该学生的 `edu_status`。
- **延期毕业必须先转班**：班级毕业是"整班毕业"，无法在班里单独留一个学生。延期毕业的学生要**先转到下一届的班**（`transfer_students` + `sync_year=True`），再执行原班毕业。否则他会跟着一起被毕业——这是批量操作最容易出的事故，毕业接口必须在确认页列出"将被毕业的学生名单"供人工过目。


### 5.4 权限矩阵（必须落到代码）

新增 `apps/common/access.py::student_can_study(user)`，在以下入口统一拦截：

| 能力 | enrolled | suspended | graduated | withdrawn |
|---|---|---|---|---|
| 登录 | ✅ | ✅ | ✅ | ✅ |
| 查看历史成绩 / 错题 | ✅ | ✅ | ✅ | ✅ |
| 进入课程、看视频 / 资源 | ✅ | ❌（休学即停学） | ✅（全部内容，不裁剪） | ✅（只读） |
| 提交作业 / 开始考试 | ✅ | ❌ | ❌ | ❌ |
| AI 助教提问 | ✅ | ❌ | ❌ | ❌ |
| 学习行为计入统计 | ✅ | ❌ | ❌ | ❌ |
| 出现在班级名单 | ✅ | ✅（标"休学"） | ✅（历史档案区） | ❌ |

**"看得到"与"算不算"分开**：毕业生、退学生仍可进入历史课程看视频（决策 4），但不计入任何统计、不参与预警、不能提交。这样既不做内容裁剪（省一套判断），也不会污染统计口径——课程属于固定学期，统计窗口随学期关闭。

**但视频进度接口不能一刀切 403**：`WatchProgressViewSet` 是播放器每 10 秒调一次的高频写入接口。对毕业生直接返回 403，播放器会持续报错、断点续播失效，最后变成"看不了"——与决策 4 冲突。

| 状态 | 视频进度写入 | 处理 |
|---|---|---|
| enrolled | ✅ 正常写 | — |
| graduated / withdrawn | ✅ **照常写** | 统计侧按 `edu_status=enrolled` 过滤，不参与任何报表与预警 |
| suspended | ❌ 403 | 前端课程页直接给"休学中，暂不可学习"空状态，正常不会进到播放页；偶发 403 可接受 |

对应的统计过滤点（都要加，漏一处就会被毕业生拉高完成率）：

```python
# analytics/services.py::build_class_stats 等
ClassStudent.objects.filter(classroom=classroom, learn_status="active",
                            student__edu_status=User.EduStatus.ENROLLED)
```

> 这也修正了一个现存口径问题：现在统计分母是"班级全员"，休学/退学生的未完成作业会一直拉低完成率。改造后分母只算在读。


课程可见范围的实现（关键，决定转专业旧课是否消失）：

```python
# 学生可见课程：本班在册关系 + 班级未归档
qs.filter(
    classes__students__student=user,
    classes__students__learn_status="active",     # 毕业保持 active，转班为 transferred
    classes__status__in=[ClassRoom.Status.ACTIVE, ClassRoom.Status.GRADUATED],
    status=Course.Status.ACTIVE,
)
```

- 毕业：`ClassStudent` 保持 `active`（5.5 第 3 条），班级 `graduated` → **课程仍可见**，符合"毕业生能看历史"
- 转专业：旧班关系置 `transferred` → **旧课自动消失**，符合决策 6
- 归档班：`archived` 不在列表 → 真正退出历史（管理员仍可查）

两条决策在这里自洽，不需要额外的"历史课程"标记字段。

| 计入统计分母 | ✅ | ❌（单列） | ❌ | ❌ |

**精确拦截点**（不存在统一的"提交"入口，必须逐处加）：

| 入口 | 位置 | 备注 |
|---|---|---|
| 作业提交 | `homework` 的 `HomeworkSubmission` create | 附件暂存 `stage_attachments` 也要拦，否则传了附件不能提交 |
| 考试开考 | `exams/views.py:256` `start` | 开考前拦 |
| 考试交卷 | `exams/views.py:397` `submit` | **不拦**：已开考的答卷必须允许交，否则学生被卡在考场 |
| 视频进度 | `courses/views.py:686` `WatchProgressViewSet` | 学习时长统计入口，写入即计分 |
| 实验提交 | `labs/views.py:342` `submit` | 同作业 |
| AI 问答 | `knowledge` 问答视图 | 休学后仍可查历史会话，不可新提问 |

> 考试的交卷例外很容易漏：如果一刀切拦 `submit`，休学当天正在考试的学生会永远交不上卷，答卷卡在 `in_progress` 状态。

### 5.5 毕业批处理

`POST /api/admin-panel/classes/<id>/graduate/`

1. **前置校验**：班级 `duration_years` 已满（或强制确认）；班级内**无进行中考试**、无未截止作业；有则列出清单要求先处理或强制标记"按已提交计"
2. **返回待毕业名单**（`GET .../graduate/preview/`），管理员确认后才执行——这是防误操作的唯一一道闸
3. 事务内：`ClassRoom.status=graduated`；把 **该班占用关系（`learn_status ∈ {active,inactive}`）且 `edu_status=enrolled`** 的学生置 `graduated`
4. `ClassStudent` **保持 active**（历史可查），不删、不置 removed
5. 课程保持可读，学生端课程列表仍可见（见 5.4 的可见性实现）
6. 写 `AdminActionLog`（新增 `Action.CLASS_GRADUATE`），记录人数与名单快照

> **第 3 条的限定条件不能省**：判定依据必须是"该班的**占用关系**"，**不是**"该班所有 `ClassStudent` 行"。`transferred`/`removed` 是历史行，若把它们也算进来，已转走的学生会被原班一起毕业——而这类学生本人在新班里毫无感知，直到某天发现自己不能再学新课。这是纯数据事故，且很难被发现（`edu_status` 悄悄变了）。
>
> v7 修正：既然转班**必然**把旧关系置 `transferred`（5.2 的 service 唯一入口保证），占用关系判定已经足够安全；再叠加 `edu_status=enrolled` 作为第二道闸，双重保险。

支持批量（按届别一次处理多个班，逐班列出名单）；支持撤销（授位审核退回，回滚到 enrolled，写审计）。

## 6. 功能 D：智课复用

### 6.1 交互

课程列表行操作「复用创建」→ 弹窗：

1. 源课程（默认当前行；管理员可跨教师选，并需指定归属教师）

5. 确认 → 异步任务 → 完成提示"已创建，内容复制完成，可前往配置章节/发布"

### 6.2 复制清单

| 层 | 内容 | 默认 | 说明 |
|---|---|---|---|
| 章节树 | `Catalog`（含 `is_published`、`order`、`intro`） | ✅ 必选 | 先父后子，重建 parent 映射 |
| 课件 | `PPTResource.file` + `parsed_pages`（含页图 URL）+ `version` | ✅ | 页图整目录拷贝并改写 URL |
| 讲稿 | `TeachingVideo.scripts[].script` | ✅ | 核心资产，纯 JSON |
| 配音 | `scripts[].audio_url` 物理文件 + `subtitle_url` / `video_url` | ✅ | 核心资产，避免重跑 TTS |
| 教学资源 | `CourseResource`（文档文件 + 预置 path 引用） | ✅ | `access_token` 重新生成 |
| 知识库 | `Material` + `KnowledgeChunk`（含 `embedding` 向量） | ✅ | 免重新 embedding，省一次全量向量化 |
| 题库 | `Question`（含题图、选项、答案、`scenes` M2M） | ⬜ 可选 | 有的教师想换题，默认不勾 |
| 作业 / 考试 | `Homework` / `Exam` + `Paper` + 题目 | ❌ 不复制 | 运行数据（含 `classroom`、提交、答卷），新班还没配 |
| 学习数据 | 进度、答题、问答、统计、错题 | ❌ 永不复制 | 属于学生个人历史，不能串 |

`Course` 新增 `reused_from = FK('self', null, SET_NULL, related_name='reused_courses')`，前端展示"由《XX》复用"。

### 6.2.1 必须处理的四类跨课程脏数据

复制不是"把行抄一遍"，有四类字段一旦盲抄就会产生错数据或越权：

| # | 字段 | 盲抄的后果 | 正确处理 |
|---|---|---|---|
| 1 | `Material.classroom` | 班级定向资料被带到新课程。若新课程挂的是另一个班，该班学生检索不到（哑数据）；若仍挂原班，则两门课的资料混在一处 | **置 `None`**（转为课程通用资料）。除非目标课程明确也挂该班，且复用弹窗里二次确认 |
| 2 | `TeachingVideo.gen_status` | 源课程 `AUDIO_READY`（有讲稿有配音、无合成视频），抄成 `DONE` 会让前端以为可播放，点开 404 | **按实际文件重算**：`video_url` 存在→`DONE`；`audio_url` 存在→`AUDIO_READY`；只有 `scripts`→`SCRIPT_READY`；全空→`DRAFT` |
| 3 | `KnowledgeChunk.embedding` | 换了 embedding 模型后维度不同，余弦检索静默算错或抛异常，表现为"AI 答非所问"且很难排查 | 复制前抽样校验 `len(embedding)` 与当前模型维度；不一致则**清空向量并标记待重建**，任务结束时提示"知识库需重建向量" |
| 4 | `Question.scenes`（M2M → SceneTag） | 只抄题目不抄用途分类，题目在练习/作业/考试三个池子里全部不可见 | 复制 M2M 关联（`SceneTag` 本身是全局字典，**不复制 tag 行**） |

另外两条不属于"脏数据"但同属复制语义：

- **新课程默认 `inactive`**：复用产出的课程不挂班、不发布。教师确认内容后再置 active 并挂班，避免"复用即曝光"。
  - 现有 `Course.Status` 只有 `active / inactive / archived`，`inactive` 的展示文案是"停用"。复用场景下它实际是"待发布"，前端在 `reused_from` 非空的课程上把 `inactive` 显示为「待发布」，避免教师困惑。若后续这类课程变多，再考虑加 `draft` 枚举值（会牵动 filterset 与前端筛选，非必要不动）
- **复用不带作业/考试**：弹窗必须显式写出"作业、考试、学习记录不会复制"，否则教师会以为拿到的是全套。

### 6.3 实现要点（按踩坑顺序）

1. **ID 映射表**：`{old_catalog_id: new_catalog_id}` 必须在复制章节后建立，后续 PPT/Video/Chunk/Material/Question 的 `catalog` 全部走映射；漏一个就是跨课程脏数据。
2. **`TeachingVideo.catalog` 是 OneToOne**：新课程每个章节最多一条视频，映射后逐条创建，不能批量 `bulk_create` 跳过唯一性。
3. **文件必须物理拷贝**，不能共享路径：`courses/views.py:752` 与 `CourseResource.perform_destroy` 都会 `file.delete(save=False)` 物理删除文件。若两课程共享同一路径，删源课程的课件会把新课程的文件一起删掉。
   - 拷贝到新 uuid 目录：`ppt/<newuuid>.pdf`、`ppt_pages/<newhash>/`、`tts/<newuuid>.wav`、`course_resources/<newuuid>.<ext>`、`materials/<newuuid>.<ext>`、题图同理
   - **顺序有坑**：页图目录名是 `ppt_pages_dirname(resource_id)`，由 **PPTResource 主键 + SECRET_KEY** 派生（`ppt_parser.py:51`）。必须"先保存新 PPTResource 拿到 id → 算出新目录名 → 拷文件 → 改写 `parsed_pages[].image`"，顺序颠倒会拷到一个永远访问不到的目录
   - `parsed_pages[].image` 里的 `/media/ppt_pages/<oldhash>/slide-001.png` 要整串替换为新 hash 目录
   - `scripts[].audio_url` 同理替换（它是 `CharField` 不是 `FileField`，ORM 不会管，最容易被忽略）
4. **`access_token` 必须重新生成**（`unique=True`），否则复用直接 IntegrityError。
5. **向量沿用不重建**：`KnowledgeChunk.embedding` 原样复制（见 6.2.1 第 3 条的维度校验）。这是复用最大的省钱点——一门课 185 个 chunk 不必重新 embedding。
6. **异步执行**：复用 `AITask`（已有信号量、进度轮询、`/api/ai-tasks/active/` 横幅恢复），新增 `task_type='course_reuse'`，`progress={stage, done, total}`，阶段：章节→课件→讲稿→配音→资源→知识库→题库。
7. **事务与失败清理**：DB 用单个 `transaction.atomic`；文件先写临时目录，成功后 rename 到正式路径，失败删除临时目录，避免孤儿文件。
8. **防重**：同一 (teacher, source_course) 存在 running 任务时拒绝新任务，避免重复复制撑爆磁盘。
9. **磁盘容量**：复用前计算源课程 media 体积并在弹窗展示（`du` 同口径），剩余空间不足直接拒绝。当前开发库 media 已 1.1G，需先确认生产盘余量。
10. **正在生成的内容不复制**：`gen_status in (composing)` 或存在 running `AITask` 的视频，只保留脚本、状态置回 `script_ready`，前端已有"补生成缺失页"能力。

### 6.4 备选方案：共享资产（不推荐作为一期）

只复制 DB 行，`file` 字段指向源课程同一物理路径：秒级完成、磁盘零增长。但必须引入引用计数（`StoredObject` 表 + 删除前检查），并改写现有两处物理删除逻辑。收益是省磁盘，代价是删除语义变复杂、迁移与备份口径变化。**建议一期用物理拷贝，等真的遇到磁盘瓶颈再演进。**

### 6.5 明确不做的事

- 不做"同一课程跨学期复用"（不新增 `ClassCourse` 到旧课程），否则作业/成绩/统计会跨学期混在一起，历史数据不可解释。
- 不做"课程版本管理/差异合并"（复用的源课程改动不会回流新课程，是快照不是分支）。

### 8.1 P1 内部的安全实施顺序（避免中间态失权）

1. 先加 `teacher_teaches()` 与新口径的过滤条件（此时班级 teacher 仍有值，两套并行，行为等价）
2. 把 19 处调用逐个替换，每替换一处跑一次对应模块回归
3. 全部替换完，再把 `ClassRoom.teacher` 改为 `null=True + SET_NULL`，原值保持不动（它从此只是「建班人」记录）
4. 最后下线邀请码与教师建班入口

> 反过来做（先置空 teacher 再改权限）会让系统在一段时间内"教师看不到作业、发不了考试"，且很难定位是哪一处没改。

## 12. 学期字典（Term）设计

已确认引入。当前 `Course.term` 是 `CharField(50, blank=True)`，仅用于展示、筛选、搜索，无业务逻辑，改动风险低。

### 12.1 模型

```python
class Term(BaseModel):
    year = models.PositiveSmallIntegerField("学年起年")        # 2026 表示 2026-2027 学年
    season = models.CharField(max_length=8, choices=[("spring", "春季"), ("autumn", "秋季")])
    name = models.CharField("显示名", max_length=50, unique=True)   # "2026春"
    start_at = models.DateField("开始日期", null=True, blank=True)
    end_at = models.DateField("结束日期", null=True, blank=True)
    is_current = models.BooleanField("当前学期", default=False)

    class Meta:
        constraints = [
            models.UniqueConstraint(fields=["year", "season"], name="unique_term_year_season"),
            models.UniqueConstraint(fields=["is_current"], condition=Q(is_current=True),
                                    name="unique_current_term"),
        ]
        ordering = ["-year", "season"]
```

`Course.term` 改为：

```python
term = models.ForeignKey("courses.Term", null=True, blank=True,
                         on_delete=models.PROTECT, related_name="courses", verbose_name="学期")
```

- `PROTECT`：有课程引用的学期不能删，只能改名——避免历史课程突然"没有学期"
- `null=True` 为迁移兼容：**保存时不强制必填**（否则迁移后 term 为空的课程连改简介都保存不了）。新建课程默认带当前学期，列表对空值标「学期待归属」（见 X-30）
- 不放到 `ClassCourse` 上：课程本身只属于一个学期，关系表再存一份必然漂移

### 12.2 迁移

1. 建 `Term` 表，按现有 `Course.term` 去重值预置（`"2026 春"` → `2026/spring`）
2. 归一化映射：去空格、全半角、`春|春季|上` → spring，`秋|秋季|下` → autumn
3. 匹配不上的课程置 `term=None`，管理端课程列表加"学期待归属"筛选，人工补齐
4. 迁移完成后把字段改名（`term_text` 留一版备份，确认无误再删）

### 12.3 影响面

| 位置 | 改动 |
|---|---|
| `courses/views.py:80` `filterset_fields=["status","term"]` | 改 `term`（FK 仍可精确匹配 id），搜索走 `term__name` |
| `platform_admin/oversight_views.py:117` `term__icontains` | 改 `term__name__icontains` |

### 12.4 与学年制的关系

- 学年 = `2026 秋 + 2027 春`，`Term.year` 记学年起年，避免出现 `2027春` 属于 `2026学年` 的歧义

## 13. 课程教师团队（评估结论：本期不做，但必须预留）

### 13.1 需求澄清

讨论中出现的"班主任"实际指向三个不同角色，必须先分开（详见 §4.1.1）：

| 角色 | 归属对象 | 职责 | 本系统现状 |
|---|---|---|---|
| 行政班班主任 | 班级 | 管学生、管学籍 | **不需要**，学籍动作全由管理员执行 |
| 课程负责人 | 课程 | 对课程内容与质量负责，可邀请协作教师 | `Course.teacher`（创建者），已存在 |
| 课程团队成员 | 课程 | 一起备课、批改、答疑 | **不存在**，即本节要评估的 |

用户描述的是第二 + 第三种：**创建课程的人 = 课程负责人，可以拉其他教师进来共同管理**。这与"行政班班主任"无关，因此 `ClassRoom.teacher` 既不能改造成班主任、也不该继续承担权限，只能降级为建班人记录（§4.1.1）。

### 13.2 结论：本期不做

| 判断维度 | 结论 |
|---|---|
| 当前规模 | 开发库 2 名教师 / 3 门课程；生产仅 1 名教师。没有并发协作的真实场景 |
| 影响面 | 需要改 41 处 `course.teacher` 权限判断；作业、考试、统计、复用、督管五个维度都要定义"多人时听谁的" |
| 与本期关系 | 组织重构本身已经动了 19 处权限锚点 + 6 个模块，再叠加团队会让 P1 无法收口 |
| 替代方案 | 现在要协作，只能让管理员把 `Course.teacher` 转移给另一个人——这会丢掉原负责人的归属，且历史作业无法追溯创建者 |

**不做，但必须预留**：本次把所有 `course.teacher_id == user.id` 的判断收敛进 `teacher_can_manage_course()`（§4.2.1）。这样将来加团队时只改函数体一行，41 处调用不动。这是本次改造里性价比最高的一个决定。

### 13.3 若要做，最小设计

```python
class CourseMember(BaseModel):
    class Role(models.TextChoices):
        OWNER = "owner", "课程负责人"
        TEACHER = "teacher", "协作教师"

    course = models.ForeignKey(Course, on_delete=models.CASCADE, related_name="members")
    teacher = models.ForeignKey(settings.AUTH_USER_MODEL, on_delete=models.CASCADE,
                                related_name="course_memberships")
    role = models.CharField(max_length=16, choices=Role.choices, default=Role.TEACHER)
    invited_by = models.ForeignKey(settings.AUTH_USER_MODEL, null=True, blank=True,
                                   on_delete=models.SET_NULL, related_name="+")
    joined_at = models.DateTimeField(auto_now_add=True)

    class Meta:
        constraints = [models.UniqueConstraint(fields=["course", "teacher"], name="unique_course_member")]
```

两层权限：

| 能力 | OWNER | TEACHER |
|---|---|---|
| 维护章节 / 课件 / 讲稿 / 配音 / 资源 | ✅ | ✅ |
| 发布作业 / 考试，批改，看全课统计 | ✅ | ✅ |
| 挂班 / 撤班 | ✅ | ❌（避免多人同时改授课范围） |
| 邀请 / 移除团队成员 | ✅ | ❌ |
| 复用本课程 | ✅ | ❌ |
| 删除课程 / 转移归属 | ✅ | ❌ |

`Course.teacher` **保留**为 owner 的冗余指针（不删），保证 41 处旧逻辑与历史数据不破；写入时与 `CourseMember(role=owner)` 同步，巡检命令兜底。

### 13.4 做之前必须先回答的六个问题

1. **作业/考试要不要记创建者**：现在 `Homework`/`Exam` 都没有 `created_by`。多教师后，"谁出的作业、谁负责批改"无法追溯。要做团队，这两个字段必须先加。
2. **批改权**：团队成员能否批改别人布置的作业？高校课程组通常可以，但责任不清。建议：默认都能批改，记录批改人。
3. **移除成员后的数据**：被移除教师创建的作业/考试保留，`created_by` 置空还是保留历史姓名？建议保留（SET_NULL + 冗余姓名快照）。
4. **邀请方式**：负责人输工号直接加入，还是发邀请待对方接受？校内信任环境建议"直接加入 + 站内通知"，省掉一套邀请状态机（待接受/已拒绝/已过期）。
5. **复用归属**：团队成员复用的课程归谁？建议归操作者本人，`reused_from` 指向源课程。
6. **督管口径**：管理端"教师覆盖学生数"按 owner 还是全体成员？建议按全体成员去重，另列 owner 维度。

### 13.5 如果只想要"协作"而不想要"团队管理"

比完整团队轻一个量级的做法：**课程共享（CourseShare）**——owner 在课程设置里填工号，把课程"共享"给某位教师，对方获得维护内容与教学的权限，但没有邀请/移除权、不能删课。没有角色概念、没有邀请流程、没有转移归属，一张表两列即可。

适合"临时搭把手"的场景。如果实际需求只是"我休假时有人能帮我发作业"，用这个就够，不必上完整团队。
