## 1. 阶段定义与准出条件

每个阶段必须**同时满足全部条件**才算完成，缺一项即未完成：

| # | 准出条件 | 判定方式 |
|---|---|---|
| 1 | 代码与 migration 完成 | `makemigrations --check --dry-run` 无遗漏 |
| 2 | L1 单元测试全绿 | `manage.py test` 0 failures / 0 errors |
| 3 | L2 真实接口验证 | curl 实测，响应体截图或输出存档 |
| 4 | L3 浏览器验证（涉及 UI 的阶段） | 真实浏览器操作 + 截图 |
| 5 | L4 迁移演练（涉及 schema 的阶段） | 在 db 副本上跑通，前后数据计数一致 |
| 6 | L5 回归清单通过 | 按阶段清单逐项打勾 |
| 7 | 测试报告落盘 | `docs/test-reports/P{n}-测试报告.md` |
| 8 | 文档同步 | 方案文档与实际实现不一致处已更新 |

**任一项不满足 → 阶段未完成 → 不提交、不推送、不进入下一阶段。**

## 2. 测试分级（什么叫"真实测试"）

| 级别 | 内容 | 工具 | 不算通过的情况 |
|---|---|---|---|
| **L1** | 业务逻辑单元/集成测试 | Django `TestCase`，独立 `test_` 库 | 只测了"函数不报错"，没断言结果；用 mock 绕过 DB |
| **L2** | 真实 HTTP 接口 | 起 `runserver 8005`，`curl --noproxy '*'` | 只跑单测不调接口；用 DRF test client 代替（掩盖路由/权限/序列化问题） |
| **L3** | 真实浏览器 | `agent-browser`，localhost，真实登录不同角色 | 只 `npm run build` 成功；只截静态图没交互；用固定 `sleep` 等异步 |
| **L4** | 迁移演练 | db 副本 + `migrate` | 只在空库跑过；没对比迁移前后数据量 |
| **L5** | 回归 | 人工 + 脚本，按清单 | "应该没影响" |

### 2.1 反例清单（出现即判定测试无效）

- 注释掉或跳过一个失败用例让它"变绿"
- 为了让断言通过而放宽业务校验（如把 403 改成 200）
- 只跑 `manage.py check` 就宣称后端通过
- 前端只 build 不打开页面；用 `sleep` 代替等待元素出现
- 用生产/开发库直接跑 E2E 并留下脏数据不清理
- 截图来自其他页面或上一次运行

## 3. 环境与数据策略

### 3.1 数据库

| 用途 | 库 | 说明 |
|---|---|---|
| L1 单元测试 | Django 自动创建 `test_*` | 不污染开发库 |
| L2/L3 | `backend/db.sqlite3` | 测试数据必须带 `e2e_` 前缀 |
| L4 迁移演练 | `backend/db.migration-test.sqlite3`（副本） | 拷一份跑 migrate，验证后删除 |

**P0 需补一个可测试性改造**：`config/settings.py` 的 SQLite 路径支持环境变量，便于迁移演练指向副本，不手工改代码：

```python
"NAME": os.environ.get("SQLITE_PATH") or BASE_DIR / "db.sqlite3",
```

不加这个，每次迁移演练都要临时改 settings 再改回来，容易忘。

### 3.2 测试数据纪律

- 账号、班级、课程一律加 `e2e_` / `测试` 前缀
- E2E 脚本结束前删除自己创建的数据（按前缀 + `created_at` 双重条件）
- 不删非本次创建的数据；删除前打印 `id / 名称 / created_at` 人工过目
- 生产库只读，任何写操作需单独授权

### 3.3 服务启动（固定命令，避免端口错乱）

```bash
# 后端（改代码后必须杀进程完整重启，autoreload 子进程会继承旧 env）
cd backend && ./venv/Scripts/python.exe manage.py runserver 8005

# 前端（改源码后先 build）
cd frontend && npm run build
cd .. && node serve-local.js
```

### P0 地基（schema + service + 巡检）

**必须做**：

1. `makemigrations --check --dry-run` → `No changes detected`
2. **迁移前先说清存量脏数据**（2026-10-29 实测）：

3. 迁移演练：`cp db.sqlite3 db.migration-test.sqlite3` → `SQLITE_PATH=... migrate` → 校验：
   - `ClassRoom` 仍 6 条、`ClassStudent` 仍 6 条、`User` 仍 8 条（冲突处理后 `ClassStudent` 可能变 6 或 7，以实际处理方式为准，但**必须有记录**）

   - 所有课程 `term` 有归属或明确为 null
4. service 单测：`assign_students` / `transfer_students` / `remove_students`

## 5. 提交与推送规则

### 5.1 提交

```bash
git add -A
git diff --cached --stat        # 自查：只包含本阶段文件
git commit -m "feat(组织重构-P0): 班级状态/学籍字段 + 单班占用唯一约束 + 入班 service + 巡检命令"
```

- 提交粒度：一个阶段可拆多个 commit，但每个 commit 必须自洽可运行
- commit message 前缀：`feat(组织重构-P{n})` / `fix(...)` / `test(...)` / `docs(...)`
- migration 文件必须与模型改动同一个 commit
- 禁止提交：`.env`、`db.sqlite3`、`media/`、`__pycache__`、临时测试脚本
- 非源码产物（`output/` 下的导出样例、汇报 xlsx、`docs/测试文件/` 下的临时样本、`test/screenshots/` 截图、`docs/计算机网络课程资料/`）已于基线段加入 `.gitignore`，正常不会再出现在 `git status` 里；若又冒出来，说明 `.gitignore` 被改坏了，先查再提交

### 5.2 推送（阶段完成的唯一出口）

**只有满足 §1 全部准出条件才允许 push。**

```bash
git status                    # 干净
git fetch origin
git log origin/feature/org-refactor..HEAD    # 确认要推的提交
git push origin feature/org-refactor
git tag p{n}-done && git push origin p{n}-done
```

- 不 push 到 `deploy/production`、不 push 到 `main`
- 生产部署**不在本规范内**，需单独授权、单独流程（scp + docker compose build，见部署 skill）
- push 失败（沙箱偶发 502）允许重试，不算阶段失败

## 6. 失败处理

| 情况 | 处理 |
|---|---|
| 测试失败 | 修代码，不修测试；禁止注释/跳过/放宽断言 |
| 连续两次修复仍失败 | 停止，回到方案层重新评估，禁止硬凑 |
| 迁移导致数据异常 | 回滚到副本快照，修正迁移后重跑全流程，不许"先上线再修数据" |
| 发现方案与代码冲突 | 先更新方案文档并记录，再改代码，避免文档与实现两张皮 |
| 阻塞（缺权限/缺数据） | 立刻说明，不擅自绕过 |
