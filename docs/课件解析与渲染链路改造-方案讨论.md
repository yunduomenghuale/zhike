# 课件解析与渲染链路改造 · 方案讨论

> 起因：评审 PPT 渲染"全局串行"时发现，课件上传链路同时存在 4 个独立问题，串行只是其中一层。
> 时间：2026-11-02 ｜ 状态：讨论稿（未实施）
> 关联：`docs/AI长任务队列化改造方案.md`（讲稿/配音队列化，本期非目标里"不动渲染"需要重新讨论）

---

## 0. 结论摘要

链路现在长这样（`courses/views.py:531-545` `perform_create`）：

```
上传字节 → 文本解析(python-pptx) → 【全局锁】渲染页图(soffice) → 向量入库(embed API) → 返回
                                     ↑ 全系统同一时刻只有 1 个            ↑ 6 批网络调用
         └─────────────────────── 全部在 1 个 gunicorn 请求线程里跑完 ───────────────────────┘
```

四个问题按严重度：

| # | 问题 | 本质 | 影响 |
|---|---|---|---|
| **P-A** | 整条链路同步跑在请求线程 | 请求线程被当执行器 | 4 个教师同时上传即全站卡死（全站只有 4 个线程） |
| **P-B** | 渲染锁把 **PDF 也罩住** | 锁的粒度大于真实约束 | 本可并发的 PDF 白白排队 |
| **P-C** | soffice 没有独立 profile | 用"全局串行"回避了本可解决的问题 | 渲染吞吐恒为 1，无法利用 32 核 |
| **P-D** | 无去重、无页图复用 | 每次上传都重渲染 | 重复文件、课程复用时重复烧 CPU |

**核心判断**："LibreOffice 必须全局串行"是**在没有独立 profile 的前提下**成立的妥协，不是硬约束。
给每次转换独立 `-env:UserInstallation` 就能并发；真正必须串行的只剩 Windows 的 PowerPoint COM，
而生产是 Linux。

**已决策**（2026-11-02）：三件事一次做完、渲染并发 2、`ppt_parse` 与讲稿同一个 worker 独立槽位。
方案见 §2（W0–W6），其中 **W0 锁槽位化是并发 2 的前置条件**——不改锁，并发永远是 1。

## 1. 逐项分析

### P-A 同步执行（最大的问题，也最容易解）

`perform_create` 里依次做四件事，一步都不能提前返回：

| 阶段 | 典型耗时（30~60 页，估算未实测） | 备注 |
|---|---|---|
| 文本解析 | 0.5~2s | python-pptx / pypdf，快 |
| 渲染页图 | 5~15s（**串行排队时间另算**） | soffice 整文件转 PDF + 逐页出图 |
| 向量入库 | 10~30s | `EMBED_BATCH_SIZE` 分批，每批一次网络调用 |
| 合计 | **20~45s**，4 人并发时叠加排队 | 期间各自占住 1 个请求线程 |

生产 `gunicorn --workers 2 --threads 2` = 4 个线程。**4 个人同时上传课件，全站 API 停止响应**，
包括登录、交作业、看视频。这是比讲稿更硬的故障面——讲稿至少是教师自己点、频率低；
课件上传是每门课的必经步骤。

**解**：把整条链路搬进 worker（新增 `ppt_parse` 任务类型），上传接口只做"存文件 + 建 PARSING 记录"，秒返。

**好消息：前端已经替我们做好了异步准备**。`CourseCatalog.vue` 里已经有一套完整的解析进度轮询：
- `pollPptParse()` 每 1s 拉 `listPpts({catalog})`，读 `parse_progress` 的 `stage/done/total`；
- 有陈旧保护（`PPT_PARSE_STALE_MS`，进度停更判失败）；
- 有"恢复轮询"分支（刷新页面后靠轮询收尾）。

它现在只是**没被用上**——因为 HTTP 请求一直挂着，走的是"响应返回即完成"那条路。
改造点很小：上传响应返回后**不要立刻置 done**，把 `httpPending` 置 false 交给轮询收尾。

```js
// 现状（CourseCatalog.vue:1937-1950）：响应一到就宣布完成
ElMessage.success('上传并解析完成')
task.phase = 'done'; task.percent = 100

// 改成：响应只表示"已受理"，交给轮询
task.httpPending = false
// 轮询发现无 active 记录时，才 finishUploadTask('done')
```

注意一个坑：改成异步后，响应立刻返回时**解析记录可能还没建好**（或刚建、`parse_progress` 还是空），
轮询第一拍会看到"没有 active 记录"→ 误判完成。修法：轮询增加"首次至少等 N 拍"或
"看 `parse_status == parsing` 而不仅仅是 active 列表"，并在上传响应里直接回 `ppt_id`，
轮询优先按 id 查。

### P-B PDF 被无谓地串行化

`render_presentation_slide_images()` 把 `_render_guard()` 包在**整个函数体外**（`ppt_parser.py:150-157`），
PDF 分支也在里面。而 PDF 走 `pypdfium2`（Chrome PDFium），本身完全可并发，也没有 profile 问题。

代码注释给的理由是"并发渲染峰值内存高，统一排队更稳"——这是**为了省事的一刀切**，
代价是 PDF 上传（很常见的路径）无条件排在 PPT 渲染后面。

**解**：锁只包 PPT/PPTX 分支。PDF 用一条独立的、更宽的并发限制（如 3），或干脆不加限制
（单页 200KB 级内存，60 页也就几十 MB）。

> 附带说明：`render_pdf_to_images()`（作业附件预览等入口，`ppt_parser.py:165`）本来就**没有**
> 走 `_render_guard`，所以线上已经存在"预览渲染可并发、上传渲染必须排队"的不一致 —— 这也反证了
> PDF 不需要那把锁。

### P-C 渲染吞吐恒为 1（真正该改的地方）

现在的命令：

```python
subprocess.run(["soffice", "--headless", "--convert-to", "pdf", "--outdir", tmp, source])
```

没有 `-env:UserInstallation` → 多个 soffice 实例共享同一个 user profile（`~/.config/libreoffice`），
并发时会互相锁 profile、导致转换失败或页图缺失。这才是"必须串行"的真实原因。

**解**：每次转换给一个独立的 profile 目录：

```python
profile = f"file:///tmp/lo-profile-{uuid4().hex}"
subprocess.run(["soffice", "-env:UserInstallation=", profile, "--headless",
                "--convert-to", "pdf", "--outdir", tmp, source])
```

并发度由**内存**而不是锁决定：每个 soffice 约 300~500MB。容器 8g（且与 gunicorn、本地模型共享），
并发 2~3 是安全区间。

比"每次新建 profile"更稳的做法是**预建 profile 池**：容器启动时建 3 个 profile 目录，
渲染时借一个、用完归还。理由：首次转换要初始化 profile（约 1s）和字体缓存，
每次新建会把这 1s 摊到每个文件上；池化后只有第一次付这个成本。

**为什么这条值得做**：32 核的机器被一把锁压成单核，渲染吞吐与硬件完全脱钩。
课程复用、批量导入课件这类场景会直接撞上这个天花板。

### P-D 没有复用

1. **同文件重传**：`PPTResource` 没有文件哈希字段，同一份 pptx 传两次就渲染两次。
   加 `file_md5` + 命中则复制页图目录，能省掉整段渲染。
2. **课程复用已做对了一半**：`reuse.py:382-387` 复制页图（`ppt_pages/<dirname>`），**不重渲染** ——
   这是正确的做法，可以作为"页图可复制"的先例。
3. **换版本重传**：`_invalidate` 会清掉旧页图，但旧文件若内容相同，本可复用。

P-D 是纯收益优化，不紧急，但成本极低（一个 md5 字段 + 一次查表）。

## 2. 推荐方案（v1.1：一次性实施）

2026-11-02 决策：**不再分期，三件事一次做完**（PPT 移出请求线程 + 渲染并发化 + 页图复用）。
代价是验证面变大，因此下面按依赖顺序拆成 6 个工作包，**W1 不通过就不进 W2**。

### W0 必须先解决的冲突：并发 2 与现有锁互斥

现有渲染锁是**互斥 1**（一个 `zhike-render-guard.sqlite` 的 `BEGIN IMMEDIATE`）。
一边说"并发 2"，一边留着这把互斥锁，结果是**并发永远是 1**，W4 白做。
所以锁必须先改造成**槽位化**，而不是简单删掉：

```
/app/data/render-guard/            ← 挪出 /tmp，跨容器共享
  slot-0.sqlite / slot-1.sqlite    ← 每个槽位一把互斥锁
/app/data/lo-profiles/
  0/ 1/                            ← 与槽位一一对应的 LibreOffice profile
```

渲染时抢任意一个空闲槽位（拿它的 `BEGIN IMMEDIATE`），用**同一个下标**的 profile 转 PDF：

```python
with render_slot() as i:                       # i ∈ [0, AI_RENDER_CONCURRENCY)
    profile = f"file:///app/data/lo-profiles/{i}"
    subprocess.run(["soffice", f"-env:UserInstallation={profile}",
                    "--headless", "--convert-to", "pdf", "--outdir", tmp, source])
```

**为什么不是"信号量 + 删掉文件锁"**：文件锁的价值在跨容器（backend 与 worker 将来都可能渲染）。
槽位化同时满足三件事——并发 N、跨容器互斥、进程崩溃由 OS 自动释放（这正是当初选 SQLite 锁库的理由）。
Windows 下 COM 是单实例，`AI_RENDER_CONCURRENCY` 强制为 1，槽位退化成现状。

> ⚠️ **v1.2 补充（自审 F2）**：必须同时**删除 `ppt_parser.py:87` 的 `_RENDER_THREAD_LOCK`**。
> 它是进程内全局互斥，包住了整个渲染函数——只改 SQLite 槽位而不动它，worker 里两线程仍会被它串行，
> 并发永远是 1。槽位本身就是并发许可，进程内再加一把锁只会限制自己。

### W1 队列内核（前置依赖）

`ppt_parse` 必须跑在 worker 里，所以**它排在讲稿队列的 B1–B4 之后**（同一套 `AITask` + claim + 心跳）。
没有队列内核，这一项无法开工。

### W2 `ppt_parse` 任务类型与上传端点

- `AITask.TaskType.PPT_PARSE`，`priority=50`（比讲稿的 100 更高优先级——教师正在上传页等着）；
- 独立槽位 **`AI_JOB_SLOTS_PPT=2`**（v1.2 修正，原写 1）：与渲染并发对齐。一个课件任务对一个文件
  只调一次 soffice，槽位 1 会让并发 2 永远用不上（自审 F1）。槽位与渲染槽位是两个概念：
  前者"几个课件在跑"，后者"几个 soffice 同时在转"，但**数值必须匹配**；
- **去重键是 `ppt` 不是 `catalog`**（v1.2 修正）：一个章节可以有多个 PPT 版本，按 catalog 去重会把
  "上传第二版"判成重复（自审 F3）。`AITask` 增加 `ppt` 外键；
- `POST /ppts/` 改：**override `create()`**（不是 `perform_create`，后者改不了响应体，自审 F9）——
  存文件 → 建 `PPTResource(PARSING)` → 入队 → **秒返** `{ppt_id, task_id}`；
- `regenerate_parse` 前端无人调用（`reparse` 只用于材料，自审 F14），保留现状或 410，不必为其做异步；
- worker 执行体复用现有三段：`parse_teaching_file_pages` → `render_presentation_slide_images` → `ingest_ppt_pages`，
  每段的 `write_progress` 回调直接沿用（`_make_parse_progress_writer` 的 0.5s 节流）。

### W3 前端两处改动

1. 上传响应返回后**不再立刻置 done**（`CourseCatalog.vue:1937-1950`），改 `httpPending=false` 交给轮询；
2. 轮询按 `ppt_id` 兜底：响应里带回 `ppt_id`，首拍查不到记录时不要判完成，宽限 2 拍（每拍 1s）。

其余展示逻辑（阶段、进度、陈旧保护、刷新恢复）**一行都不用改**——它本来就是为异步写的。

### W4 渲染并发化

- 锁槽位化（W0 已建）+ profile 池（容器启动时预建 2 个，避免每次初始化付 1s）；
- **进程内 `_RENDER_THREAD_LOCK` 删除**（v1.2，自审 F2）：否则 worker 内仍被串行；
- 只给 PPT/PPTX 分支占 CPU 槽位；PDF **不占 PPT 槽位，但走独立信号量 3**（v1.2，自审 F4：
  可并发 ≠ 无限并发，10 个 PDF 同时渲染会打爆内存）；
- 槽位获取用**逐槽 `timeout=0.2` 轮询 + 全忙 sleep 0.5 重试**，总超时 600s（自审 F11：
  对每个槽位用长 timeout 会卡死在 0 号槽）；
- `AI_RENDER_CONCURRENCY=2`、`AI_PDF_RENDER_CONCURRENCY=3` 起步。

### W5 页图复用（P-D）

- `PPTResource` 加 `file_md5`（上传时算，8MB 文件约 30ms，可接受）；
- 命中同 md5 的历史资源 → **复制页图目录 + 复制 `parsed_pages`**，跳过文本解析与渲染；
- **embed 仍然执行**：`KnowledgeChunk` 是按课程/章节归属的，换个课程上传同一份课件仍需重建片段；
- 课程复用链路（`reuse.py:382-387`）已经这么做了，W5 只是把"同文件"场景补齐。

### W6 验收

见 §3。

**顺序图**：

```
W0 锁槽位化 ──┐
              ├─→ W4 渲染并发化 ─┐
W1 队列内核 ──┴─→ W2 ppt_parse ──┴─→ W3 前端 ─→ W5 md5 ─→ W6 验收
```

W0 可以先做（不依赖队列，改完仍是互斥 1，行为不变，只是锁路径变了）；
W4 才真正把并发提到 2。

## 3. 风险与验证

| 风险 | 说明 | 应对 |
|---|---|---|
| soffice 并发仍可能不稳 | 独立 profile 是通行做法，但 LibreOffice 对并发不是官方承诺 | 灰度：并发=2 观察一周失败率；失败自动降级回串行并告警 |
| 内存打爆 | 每个 soffice 300~500MB，容器 8g 与 gunicorn/本地模型共享 | 并发上限走 env；worker `mem_limit` 单独设；压测 3 个 60 页课件同时转换 |
| 异步后"解析没开始"被误判完成 | 前端轮询第一拍可能看不到 active 记录 | 上传响应回 `ppt_id`，轮询以 id 为准 + 首次宽限 2 拍 |
| 学生看不到课件的时间变长 | 异步后有排队，页图生成前 `is_active=False` | 进度条已有；超时提示要写"前面还有 N 个课件在解析" |
| 与讲稿队列抢槽位 | `ppt_parse` 与讲稿同 worker，若槽位共享会互相挤 | 按类型独立槽位；`ppt_parse` priority 更高 |

**验证口径**（第二期完成后）：

1. 4 个教师同时上传 60 页 PPT：`GET /api/courses/` 等普通接口 P95 无劣化（对比基线）；
2. 上传响应 < 2s，课件在 60s 内变 `DONE`；
3. 解析中刷新页面，进度条从当前阶段继续，不重头开始；
4. `docker kill worker` 后重启，`PARSING` 状态的任务被回收并跑完。

## 5. 与讲稿队列方案的关系（已修订）

原队列方案 §2 把"不改 PPT 渲染"列为非目标，理由写的是"LibreOffice 必须串行"。这个理由两条都站不住：

- **"必须串行"只在没有独立 profile 时成立** → W0/W4 已把它变成并发 2；
- **"不该在请求线程里跑"比原来认为的更严重**（课件上传是每门课必经步骤，4 人同时上传全站停摆）→ W2 纳入队列。

因此主方案已同步修订：PPT 解析从"非目标"移入范围，任务类型 `ppt_parse` 与讲稿/配音共用一个 worker。
**排期上它必须在队列内核（B1–B4）之后**，因为 `ppt_parse` 完全依赖 claim / 心跳 / 回收那套机制。

与讲稿链路的两个交互点：

1. **共用 `embed` 闸门**：`ingest_ppt_pages` 与讲稿的 `embed_ingest` 都走同一个 embed 信号量，
   否则课件入库会绕过预算（这也是 W2 必须排在闸门实现之后的隐含原因）；
2. **共用 `parse_progress` 节流写入器**：沿用 `_make_parse_progress_writer` 的 0.5s 节流，
   不要在 worker 里另写一套，否则前端进度会出现两套口径。

## 7. 方案自审：不足与冲突（v1.2，2026-11-02）

按 v1.1 逐条回到代码取证的结论：**16 项问题，3 项会直接让方案失效**。
其中 F1 是我自己把参数写错了（用户选的是"渲染并发 2"，我却把课件任务槽位设成 1）。

### 7.1 阻断级（不改则方案无效）

#### F1 · 槽位 1 × 渲染并发 2：并发 2 永远用不上

`AI_JOB_SLOTS_PPT=1` 表示同一时刻只有 1 个课件任务在跑；而一个任务对**一个文件只调用一次
`render_presentation_slide_images`**（`ppt_parser.py:121-157`，PPT 走一次 soffice 转换，
出 PDF 后的逐页出图是 pypdfium2，不占渲染槽位）。所以全局任何时刻最多 1 个 soffice 进程。

**结论**：`AI_JOB_SLOTS_PPT` 必须 = `AI_RENDER_CONCURRENCY` = 2，否则 W4 做完了也看不到任何变化。
内存核算：2 × soffice(~400MB) + 2 × pypdfium2 峰值 + Django ≈ 2GB，8g 容器有余量
（若 embed=local 再叠 2.3GB 则接近上限，见 F15）。

#### F2 · 进程内 `_RENDER_THREAD_LOCK` 会把并发压回 1

v1.1 的 W0 只讲了 SQLite 锁槽位化，**漏掉了 `ppt_parser.py:87` 的 `threading.Lock`**。
它包住了整个渲染函数（`_render_guard()` 第一行 `with _RENDER_THREAD_LOCK:`），同一进程内
两个任务线程会被它串行——SQLite 槽位改造得再对，worker 里仍然是 1。

**修**：把 `threading.Lock` 的职责合并进槽位获取（槽位本身就是并发许可），直接删除；
或在进程内再加一层 `BoundedSemaphore(N)` 与槽位数对齐（冗余但更直观）。**删掉更干净**，
因为跨进程锁已经承担了互斥，进程内再加一把只会限制自己。

#### F3 · 唯一索引照搬 `(task_type, catalog)` 会把"上传新版本"判成重复

§4.2 的约束是为讲稿/配音设计的（一个章节一个。可实际一个章节可以有**多个 PPT 版本**，
`version` 就是为此递增的，`views.py:539-541`）。若 `ppt_parse` 也用 `(task_type, catalog)`，
教师传第二版课件时会命中已有任务、返回旧 task_id，新文件永远不解析。

**修**：`AITask` 增加 `ppt` 外键（nullable, CASCADE），`ppt_parse` 的唯一约束改为
`(task_type, ppt)` where `status in (pending, running)`；讲稿/配音仍用 `catalog`。
两个约束互不干扰，且 `reparse` 去重也顺带解决。

### 7.2 高危（影响正确性或稳定性）

#### F4 · "PDF 完全不上锁"会把并发从 1 直接打成 N

E5 写的"完全不上锁"是过度矫正。pypdfium2 可并发 ≠ 可以无限并发：10 个教师同时传 10 份 PDF，
就是 10 个渲染同时跑、每份几十页 PNG，内存与 CPU 双爆。

**修**：PDF 走**独立的宽限信号量**（默认 3），与 PPT 的槽位互不阻塞。
这样"PDF 不再排在 PPT 后面"与"PDF 不会无限并发"同时成立。

#### F5 · 换课件时"先删旧片段、再建新片段"造成 QA 空窗（既有缺陷，异步化后放大）

`views.py:583-590` 的顺序是：解析成功 → `is_active=False` → invalidate 讲稿 →
**删除旧版本 KnowledgeChunk** → 然后才 `ingest_ppt_pages`（失败静默返回 0）。

同步时代这个窗口是秒级；异步化后窗口 = 排队 + 解析 + 入库，且新增"worker 中途被杀"这一
失败模式 → **课程可能永久没有任何课件向量**，而 QA 侧只会表现为"答得很差"。

**修**：改成"先建后删"——新片段按 `ppt` 维度写入成功后再删旧版本的片段；
`ingest` 返回 0 时保留旧片段（与 `ingest_material` 的既有语义一致）。

#### F6 · 换课件成功即 invalidate 讲稿，会与在跑的 `script_gen` 任务打架

`views.py:587` 在解析成功后立刻调 `_invalidate_teaching_video_for_new_ppt(catalog, ppt)`，
会清空 `video.scripts` 与观看进度。若此时有 `script_gen` 任务针对**旧 PPT** 正在跑，
它会在几分钟后把旧讲稿写回这个已被重置的 video —— 数据错配，且 `is_published` 可能被置回 True。

**修**：① 任务每次落库前校验 `payload.ppt_id == video.ppt_id`，不一致即取消任务；
② invalidate 与 `page_store.merge_pages` 用**同一把 video 行锁**（`select_for_update`），
避免"清空"与"写回"交错。

### 7.5 对 v1.1 参数的修正（不改变已定方向）

| 项 | v1.1 | v1.2 | 理由 |
|---|---|---|---|
| `AI_JOB_SLOTS_PPT` | 1 | **2** | 与渲染并发对齐，否则 F1 让并发形同虚设 |
| PDF 处理 | 完全不上锁 | **独立信号量 3** | F4：可并发 ≠ 无限并发 |
| 进程内锁 | 未提及 | **删除** | F2：会把并发压回 1 |
| `ppt_parse` 去重键 | `catalog`（沿用） | **`ppt`** | F3：一个章节有多个版本 |
| 上传响应 | "秒返 `{ppt_id}`" | "override `create()`，秒返 `{ppt_id, task_id}`" | F9 |

> 以上修正**不改变** 2026-11-02 的三项决策（一次性实施 / 渲染并发 2 / 同 worker 独立槽位），
> 只是把参数与实现挂点改对。
