# 管理端「管理概览 / 教学监管」能力架构分析

> 分析时间：2026-10-19
> 分析对象：`platform_admin` 后端 + `views/admin/*` 前端（管理概览、教学监管两页为重点，对照用户管理、大模型配置两页）
> 视角：系统设计与架构合理性，不涉及具体排期

---

## 一、结论先行

1. **管理员的两个页面不是"实现烂"，而是"角色定位断层"**。需求规格说明书明确将管理员定义为「可选的平台基础运维角色，不作为一期核心业务角色」，职责是账号管理、平台配置、模型接口配置、文件存储配置、日志查看。当前实现忠实执行了这个定位：用户管理和 AI 配置两页做得相当深，教学监管只做到「资源清单」层。
2. **「督管」的产品语义天然高于「运维」**：它要求跨租户的教学过程可见性、异常发现能力、有限干预能力。现状缺的正是这一层，而不是底层数据。
3. 最需要动的架构点只有三个：**① 平台级聚合读服务（复用而非重写）② 管理端写操作审计 ③ 概览/督管的信息架构重组（指标 → 趋势 → 异常 → 明细的漏斗）**。其余是增量增强。

---

## 二、现状盘点（事实基线）

### 2.1 管理端四个页面的成熟度对比

| 页面 | 读能力 | 写/动作 | 审计 | 评价 |
|---|---|---|---|---|
| 用户管理 | 列表 + 角色/状态/关键字筛选 + 分页 | 建/改/停复用、重置密码、Excel 批量导入（模板→预览→整批事务确认） | 无 | **超出运维预期，成熟** |
| 大模型配置 | 能力矩阵 + 连接测试 + 调用流水（多维筛选）+ 汇总统计 + CSV 导出 + 字段级变更记录 | 配置保存、连接测试、全站向量重建 | AICapabilityChangeLog（字段级） | **超出运维预期，成熟** |
| 教学监管 | 课程/班级两个 tab：清单 + 搜索 + 状态筛选 + 分页，仅 annotate 计数 | 课程状态下拉内联修改；班级只读 | 无 | **停在资产清单层** |
| 管理概览 | 4 张计数卡 + 3 个百分比 + 最近 6 用户 + 最近 6 课程 | 无（刷新 + 2 个跳转按钮） | 无 | **运维看板及格，督管入口不合格** |

### 2.2 用户抱怨的技术对应

- 「只能看到数量」：概览页是 `COUNT(*)` 聚合 + 两个 top-6 列表，无时间趋势、无告警、无下钻入口；教学监管的表格只有 `class_count / student_count / course_count` 三个计数字段。
- 「看不到具体内容」：没有任何 drill-down 端点——不存在课程详情（章节/课件/题目/作业/考试 + 各班统计）、班级详情（学生进度）、教师详情（资产 + 活跃度）。
- 「不能执行基础的管理功能」：全端只有「改课程状态」一个跨租户写动作；班级状态不能管、无批量操作、无导出、无任何干预留痕。

## 三、架构层面逐项分析

### 3.1 角色定位：需求文档与产品语义的断层

需求规格说明书原文：「管理员（可选）……用于平台基础运维，不作为一期核心业务角色」。

- 当前实现 = 需求文档的**正确落地**。所以「过于简单」不能记为实现缺陷，而是**产品定位需要升级**：从「运维者」演进为「运营治理者」。
- 但升级必须克制。建议确立明文架构原则：**平台管理员 = 全局只读 + 白名单式有限干预 + 全程审计**。删除类操作一律不开放（或仅超级管理员 + 二次确认）；成绩、提交记录等教学过程数据对管理员只读。一旦管理端能改成绩/删提交，行级权限模型（`common/access.py` 的角色 → queryset 设计）就失去意义。

### 3.2 数据架构：数据全部都有，缺的是「平台级读模型」

教学全过程数据早已落库，且粒度足够：

| 监督维度 | 已有数据 |
|---|---|
| 内容资产 | Catalog、PPTResource（含 parse_progress 阶段/失败态）、KnowledgeChunk、Question |
| 教学过程 | Homework/HomeworkSubmission、Exam/ExamSubmission/score_released、Lab/LabSubmission |
| 学习行为 | VideoWatchProgress（页码/位置/完成态）、AnswerRecord、QARecord |
| AI 产线 | AICallLog（capability/scene/provider/success/is_mock/latency/tokens/trace_id） |

关键架构缺口：**教师端 analytics 已有成熟的班级聚合逻辑（`build_class_stats`：逐学生进度 + 预警），但它是教师行级视角（`classroom.teacher == request.user`），平台侧没有任何复用入口**。`platform_admin` 里的 overview 是裸 `count()`，teaching 是 `annotate(count)`——没有任何跨租户聚合服务层。

正确做法：把聚合逻辑抽取为显式 scope 参数的服务函数（如 `build_class_stats(classroom, course, scope=teacher|admin)`），平台端复用；**绝不在 platform_admin 里重写一遍统计**——那是双份维护和双份漂移。

### 3.3 权限与安全：一个真实的架构隐患

- `common/access.py` 的设计是「角色 → queryset 范围」，admin 天然全局可见。**读全局没问题**。
- 但 `AdminCourseStatusView` 允许管理员**跨教师写业务数据**，且：无审计日志、不通知教师、未定义下游联动（课程归档后，关联班级/进行中考试/学生可见性如何变化？）。对比 AI 配置变更有字段级 `AICapabilityChangeLog`——**教学侧干预是「无痕」的**。这是当前最需要在架构上补的洞。
- 另一个前瞻约束：若开放「下钻到学生明细」的读路径，必须明确其为只读语义，并在 API 层与教师端只读端点区分（管理端视图不继承 IsTeacher 的行级过滤，靠 IsPlatformAdmin 放行，属于有意设计，但应有文档标明）。

### 3.4 API 架构：三个具体问题

1. **Dashboard 式巨对象**：`/admin/overview/` 一次返回 users/teaching/recent_* 全量 blob。作为看板端点可以接受，但不可组合、不可下钻。应拆分为：看板聚合（保留）+ 资源 detail 端点 + 时间序列端点（图表消费）。
2. **缺少 drill-down 端点**：需新增课程详情（内容资产 + 作业考试 + 各班统计）、班级详情（学生进度，复用聚合服务）、教师详情（档案 + 资产 + 活跃度 + AI 消耗）。
3. **风格不一致**：platform_admin 全部是 `APIView` + 手写分页（`_paginated_response`），其余 app 均用 `ViewSet`。不是错误，但新增下钻端点时会持续放大维护成本；至少统一分页/过滤/序列化三件套模式。

### 3.5 前端信息架构

- **管理概览是纯静态卡片**：全站无 ECharts，概览无图表、无趋势、无告警区、无快捷操作。指标卡（平台用户/课程/班级/学习关系）全是绝对值，没有「比上周」。
- **教学监管是「清单表格 + 一个内联动作」**：无行点击下钻、无批量操作、无导出、无「内容完整度 / 教学进度 / 最近活跃」列。管理员回答不了业务问题：「哪门课建了目录没传课件」「哪个老师两周没动静」「多少作业待批改、多少成绩未发布」。
- **导航只有一级菜单**，督管的三个自然维度（课程 / 班级 / 教师）没有形成可扩展的信息架构；「待办/异常」没有承载位置。

### 3.6 非功能性

- overview 每次全表 `COUNT(*)`：当前 SQLite 数据量下无感知，数据增长后成为慢查询，且无缓存。规模上来后需要汇总表或定时聚合——**现在不必做**，但趋势类端点设计时要预留（按日聚合可加索引解决）。
- 管理端接口无 throttle（已知中危，全站问题）。
- 需求中的「日志查看」只覆盖了 AI 侧（调用流水 + 配置变更），**操作审计日志、登录日志缺失**。

## 四、改造建议（按投入排序，两层推进）

### 第一层：运营可见性（不新增数据模型，纯读路径 + 前端）

**概览页重组为「指标 → 趋势 → 异常 → 明细」漏斗：**
- 指标卡可点击，跳转到对应监管页并预置筛选；
- 新增 7/30 天趋势序列（新增用户/课程/班级，日粒度，供图表端点）；
- 新增「待办与异常」区：待批改作业数、未发布成绩的考试数、AI 近 24h 失败率与 Mock 回退（stats 接口已有 alerts 逻辑，直接复用）、解析失败课件、长期未活跃教师/班级。

**教学监管重组为三个维度 tab（课程 / 班级 / 教师）：**
- 课程表增列：章节数、课件数、题目数、进行中作业/考试数、最近内容更新时间；行点击开详情抽屉（内容资产清单 + 各班统计）；
- 班级表增列：作业提交率、考试完成率、预警学生数（复用班级聚合服务）；
- 新增教师维度：资产数、活跃度、AI 消耗（AICallLog 已有 triggered_by 维度）；
- 两个表都支持 CSV 导出（复用 AI 流水导出的 BOM + 上限保护模式）。

### 第二层：治理与审计（需新增模型）

- **AdminActionLog**：actor / action / target / old→new / at，覆盖所有管理端写操作（课程状态、账号变更、向量重建、AI 配置——后者可逐步迁移到统一审计）。这是「督管」可信度的地基：没有审计的干预权不可交付。
- **干预边界规则**：状态变更须在前端明示下游影响（学生可见性/进行中考试）；敏感操作二次确认；超级管理员专属操作分级。
- 趋势数据量上来后再评估统计汇总表 / 定时任务聚合；当前实时聚合足够。

## 五、风险与不做清单

- **不做**：把管理员做成「超级教师」（开放教学过程写权限）——权限模型失守，且与需求定位冲突。
- **不做**：删除课程/班级等破坏性操作入口——外键 CASCADE 下后果不可逆，如确需支持，仅超级管理员 + 审计 + 备份提示。
- **谨慎**：跨租户统计的实时全表聚合，随数据量增长需关注查询计划；先加索引与上限保护，再考虑缓存。
- 现状与需求文档一致，改造前建议先在产品层确认「督管」的职责边界（看到哪一级、能改哪一些），再落 API——否则容易做成四不像。
