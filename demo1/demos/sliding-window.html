可靠数据传输的核心思想
从一个简单的问题出发，逐步构建可靠传输协议的完整框架
教学模式：启发式，问题驱动 — 每个问题引出一个关键机制
1
如何确保手机短信被收到？
→ 确认机制：接收方收到数据后，向发送方返回确认（ACK），表示"我已收到"。没有确认就认为发送失败。
计算思维：协议 — 双方约定通信规则
2
接收方如何知道接收的分组正确？
→ 差错检测机制：发送方在数据中附加校验码（如CRC），接收方通过校验码检测数据是否在传输中出错。
计算思维：纠错 — 检测并处理数据错误
3
接收方如果接收到有差错的分组如何办？
→ 否认机制（NAK）：接收方检测到差错后，返回否认（NAK），告诉发送方"数据有错，请重传"。或者直接丢弃错误分组，让发送方超时重传。
计算思维：纠错 — 主动反馈错误信息
4
分组丢失如何处理？
→ 超时重传：发送方每发送一个分组就启动一个定时器，如果在规定时间内没有收到确认，就认为分组丢失，自动重传。
计算思维：时序 — 用定时器处理不确定性
5
确认丢失会导致什么问题？
→ 重复数据：如果ACK丢失，发送方会重传，接收方就会收到重复的数据。→ 如何解决？→ 数据分组编号：给每个分组编号，接收方通过编号判断是否是重复数据，重复就丢弃。
计算思维：协议 — 用编号解决重复问题
6
确认分组迟到会导致什么问题？
→ 重复确认：如果ACK迟到，发送方已经重传，之后又收到迟到的ACK，可能导致混乱。→ 如何解决？→ 确认编号：给ACK也编号，发送方通过编号判断是哪次的确认，避免混乱。
计算思维：时序 — 用编号解决迟到问题
7
停止等待协议的信道利用率高吗？
→ 很低！停止等待每发一帧必须等待一个RTT才能发下一帧，信道大部分时间空闲。→ 如何改进？→ 流水线方法：连续发送多个分组而不等待确认，这就是滑动窗口协议的核心思想。→ 引出连续ARQ和滑动窗口协议。
计算思维：并行/折衷 — 流水线提高并行度，但增加复杂度

从停止等待到滑动窗口 — 递进关系

停止等待(SW)：窗口=1，每发一帧等一个ACK → 回退N帧(GBN)：发送窗口=N，连续发送，出错回退重传 → 选择重传(SR)：发送窗口=N，接收窗口=N，只重传出错帧
三种协议是可靠传输的递进演化：从最简单到最高效，体现了折衷的思想 — 效率越高，复杂度越大。

为什么需要编号？

编号是可靠传输协议中最关键的机制之一 — 它解决了确认丢失和确认迟到带来的重复问题

数据分组编号

给每个发送的数据分组分配一个序号（0, 1, 2, 3, ...）。接收方通过序号判断：

1. 是否是新数据（序号=期望序号）→ 接收并交付上层

2. 是否是重复数据（序号<期望序号）→ 丢弃，但重新发送ACK

场景：ACK丢失
发送方发分组0 → 接收方收到，回ACK0 → ACK0丢失 → 发送方超时，重发分组0 → 接收方收到分组0（序号=0，但已收到过）→ 丢弃重复数据，重发ACK0

确认分组编号

给每个ACK也分配序号，表示"我已正确收到序号n及之前的所有分组"。发送方通过ACK序号判断：

1. 是否是新确认（ACK序号≥基址）→ 窗口向前滑动

2. 是否是重复/迟到确认（ACK序号<基址）→ 忽略

场景：ACK迟到
发送方发分组0 → 接收方回ACK0 → ACK0迟到 → 发送方超时，重发分组0 → 接收方重发ACK0 → 发送方收到第一个ACK0 → 又收到迟到的ACK0 → 忽略重复确认

编号空间与窗口大小的关系

序号空间大小为 2^k（k为序号比特数），必须满足：
SW协议：只需1比特编号（0和1交替）
GBN协议：序号空间 ≥ N+1（窗口大小+1）
SR协议：序号空间 ≥ 发送窗口+接收窗口（Ws+Wr ≤ 2^k）

如果编号空间不够大，窗口滑动后新旧序号会重叠，接收方无法区分新分组和旧分组！

信道利用率分析

信道利用率 = 有效发送时间 / 总时间（发送时间 + 等待确认时间 + 重传时间）

U = (N × Tf) / (N × Tf + RTT)
Tf = 发送时延，RTT = 往返时延，N = 窗口大小

假设：帧长1000字节，数据率1Mb/s，RTT=20ms，N=4，丢失帧=1号帧

SW 停止等待

~28.6%
N=1，每发一帧等待一个RTT
U = Tf / (Tf + RTT)
= 8ms / (8ms + 20ms)
≈ 28.6%
绝大部分时间在等待！

GBN 回退N帧

~61.5%
N=4，连续发4帧再等确认
U = 4×Tf / (4×Tf + RTT)
= 32ms / (32ms + 20ms)
≈ 61.5%
利用率大幅提升

SR 选择重传

~61.5%
N=4，连续发4帧再等确认
U = 4×Tf / (4×Tf + RTT)
= 32ms / (32ms + 20ms)
≈ 61.5%
无差错时与GBN相同

关键结论

1. 停止等待的信道利用率极低 — 这正是从SW演进到滑动窗口的根本原因
2. 窗口越大，利用率越高 — 但受限于序号空间和缓冲区大小
3. 无差错时GBN和SR利用率相同 — 都是流水线发送，效率一样
4. 流水线是核心改进 — 从"发一帧等一帧"到"连续发多帧"，本质是并行化

可靠传输中的计算思维要素

可靠数据传输协议的设计蕴含了丰富的计算思维要素

📜
协议
发送方和接收方约定通信规则（ACK/NAK机制、编号方案、窗口大小），确保双方行为协调
⏱️
时序
超时定时器处理不确定性；编号解决确认迟到；窗口滑动控制发送节奏
🔧
纠错
差错检测（CRC校验）、否认反馈（NAK）、超时重传 — 多层纠错保障可靠性
⚡
并行
流水线发送 — 连续发送多个分组而不等待确认，提高信道并行利用率
🔗
串行
停止等待 — 每发一帧必须等待确认，严格的串行模式，效率低但简单可靠
⚖️
折衷
效率vs复杂度：SW最简单但效率最低；SR效率最高但最复杂。GBN是折衷方案

折衷的体现

SW → GBN → SR 的演进过程就是不断在效率和复杂度之间寻找折衷：
• SW：效率最低，复杂度最低（无需缓冲区，无需编号空间）
• GBN：效率中等，复杂度中等（需要发送缓冲区，累积确认简化接收端）
• SR：效率最高，复杂度最高（需要发送+接收缓冲区，独立确认，序号空间要求最大）

思考题

思考题1：为什么SW只需要1比特编号？

停止等待协议中，数据分组编号只需要0和1交替使用就够了，为什么不需要更多编号？

SW协议中发送窗口=1，任何时刻只有一个分组在传输中。
接收方只需区分"这是新的分组"还是"这是重传的旧分组"。
用0和1交替编号：第一次发0，重传还是0，下一次发1，重传还是1。
接收方收到序号=期望序号 → 新数据；收到序号≠期望序号 → 重复数据，丢弃。

思考题2：GBN为什么使用累积确认？

GBN协议中接收端使用累积确认（ACK n表示n及之前所有分组均已收到），为什么不使用独立确认？

1. 接收窗口=1，只按序接收，乱序分组直接丢弃 → 不需要独立确认乱序分组
2. 累积确认简化了接收端逻辑 — 只需记住一个期望序号
3. 即使ACK丢失，后续的ACK也能"补上"之前的确认（如ACK3隐含了ACK0、ACK1、ACK2）
4. 缺点：如果某个ACK丢失，发送方可能不必要地回退重传

思考题3：SR的序号空间为什么要求Ws+Wr≤2^k？

选择重传协议中，为什么要求发送窗口大小+接收窗口大小≤序号空间大小？

如果Ws+Wr > 2^k，窗口滑动后新旧序号会重叠。
例如：k=2，序号空间=4(0,1,2,3)，Ws=3，Wr=3
发送方发送0,1,2 → 接收方收到0,1,2，窗口滑到3,0,1
发送方窗口滑到3,0,1 → 发送3,0,1
接收方收到0 → 这是新的0还是旧的0？无法区分！
所以必须Ws+Wr ≤ 2^k，确保窗口不重叠。

思考题4：从SW到SR，复杂度增加了什么？

从停止等待协议演进到选择重传协议，发送端和接收端各增加了哪些复杂度？

发送端增加：
1. 需要缓冲N个未确认的分组（SW只需1个）
2. 需要为每个分组维护独立的定时器（SW只需1个）
3. 需要管理发送窗口的滑动

接收端增加：
1. 需要缓冲N个乱序到达的分组（SW和GBN不需要）
2. 需要独立确认每个正确收到的分组（GBN只需累积确认）
3. 需要管理接收窗口的滑动和按序交付

这是折衷的体现：效率越高，复杂度越大。
